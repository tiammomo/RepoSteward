# RFC：RepoSteward 的长期治理方向

关联 [Issue #70](https://github.com/tiammomo/RepoSteward/issues/70)。本 RFC 的合并确认设计方向，
**不启用新的自治等级，也不授予模型公开写入权限**。当前行为以实现、可信用户配置、
[协议能力表](protocol-map.zh-CN.md)与具体操作门禁为准；后续能力分别通过聚焦 Issue / PR 交付。

## 用户、价值与产品形式

首要用户是同时维护多个仓库的个人维护者，也包括向他人项目提交贡献的开发者。用户可以继续使用
Codex、Claude Code、Copilot 等已有开发界面；RepoSteward 保存跨项目、跨会话的工作事实，并帮助
定位代码、恢复任务、独立验证、跟进评审及安排下一步。是否使用托管 Harness 是单独的选择。

长期定位是**本地优先、使用维护者个人身份、受人类规则和确定性策略约束的模型自治仓库治理控制面**。
价值应由实际结果证明：减少重新理解项目与恢复任务的成本，提高经独立验证的交付率，降低重复提案、
遗漏评审和过期证据带来的返工。报告 token 用量时，同时呈现任务质量、失败、重试和人工纠正成本。

产品入口保持互补：插件 skills 指导常见动作，CLI 支持明确的操作，MCP 提供作用域内的工具，
FastAPI + React 工作台展示项目、WorkItem、验证及异常。A2A 按已实现的能力协作，不因采用协议名就
宣称可以远程控制任意 Agent。工作台优先回答“管理哪些项目、为什么阻塞、证据是否新鲜、下一步由谁执行”。

不在本 RFC 中引入跨租户云平台、自治组织、替代所有 Coding Agent 的聊天界面或新的平行事实台账。
没有实际规模和运维证据前，维持清晰分包的本地应用与现有持久队列，无需先拆成微服务。

## 当前事实与目标边界

| 领域 | 当前能力 | 仍需独立交付或证明 |
| --- | --- | --- |
| 项目理解 | 关联本地/远程项目、源码索引、带来源的有界查询 | 陌生项目定位与影响分析的真实任务质量 |
| 任务连续性 | WorkItem、attempt、Context Pack、Checkpoint、接续包与接收记录 | 各客户端实际接续收益、条件性生命周期 hooks |
| 记忆和 skills | 作用域知识、候选审阅/撤回、按版本使用采集 | 基于效果证据的候选晋升和回退流程；模型不能自行改权限 |
| 验证 | 受信任命令、隔离快照、Runner、持久验证队列 | 新语言和项目须逐个验证，测试通过不等于模型完成任务 |
| GitHub 维护 | 人工审阅 Issue-to-PR、Portfolio、依赖、原生门禁、显式合并和审计 | 现有贡献者 PR 的原生来源登记由 #149 承接 |
| 评测 | 确定性 RepoStewardBench、用量采集；CI 归档由 #90 验收 | 可比较的真实模型任务集和长期质量数据 |
| 自治 | 用户显式授权下的受控操作与队列 | 下述 Shadow Steward 和逐级自治尚未因此 RFC 实现 |

[#155](https://github.com/tiammomo/RepoSteward/pull/155) 交付；本 RFC 复用其结构，不重复创建同一文档
拆分 Issue。当前源码结构见[源码目录指南](source-layout.zh-CN.md)，状态与数据流见[架构说明](architecture.md)。

## 人与模型的责任

维护者定义使命、优先项目、贡献范围、预算、风险边界和升级条件；审核治理章程、权限变更及异常，
保留人工接管、暂停、撤销和终止权。模型产出的建议、信心或评审文本都不能改变这些权限。

| 角色 | 工作与输入 | 隔离及输出 |
| --- | --- | --- |
| Steward | 读取项目事实、Issue、PR、CI、阻塞和历史结果，提出有界下一步 | 输出引用证据的计划；不把远程正文视为指令或授权，不持有 GitHub 凭据 |
| Builder | 在受审阅任务的独立工作区实现一个能力 | 返回变更、假设、风险和待核验结果；不能改可信配置、验证规则或自身权限 |
| Reviewer | 根据任务契约、完整 diff、独立验证及新鲜线上事实审查 | 使用独立会话和评审输入；结果绑定精确 head/base 与证据，不能沿用 Builder 的自我结论 |
| 确定性控制面 | 校验权限、作用域、新鲜度、幂等键与当前状态 | 负责凭据、租约、隔离验证、公开写入和持久审计；模型输出只能作为输入数据 |
| 维护者 | 对目标、边界、授权及最终交付负责 | 处理高风险、争议和未知结果；调整权限需新的可信记录 |

同一模型供应商的不同会话只提供逻辑隔离，不保证独立正确性；模型 Reviewer 也不满足 GitHub 要求
的另一位人类审批者。单维护者自审只能使用已经明确启用的可信策略，不能借角色名称伪造第二人。
Builder/Reviewer 不共享可写工作区、模型长期记忆或含凭据的环境；控制面保存归一化证据供双方核对。

GitHub 动作始终属于配置和实际认证一致的个人账号。模型名称或原生 session ID 不构成发布身份。
自动化运行、成本与决策审计默认留在本地，不自动发布聊天、记忆或内部日志；对外的 PR 说明和
自动化披露仍遵守目标仓库的贡献要求。不得伪造评审、贡献归属、实现过程或验证记录。

## 以项目和动作限定自治等级

以下是目标分级，**不是当前配置项或新增 CLI 命令**。每次晋升必须绑定一个项目、允许的动作类型、
有效期、预算、风险范围和可撤销的章程版本。更高等级不能扩大到其他仓库或绕过下层门禁。

| 等级 | 允许的目标行为 | 必须保留的边界 |
| --- | --- | --- |
| L0 人工推进 | 当前明确审阅、独立命令和环境开关驱动的流程 | 所有现有门禁；没有默许的后台写入 |
| L1 Shadow Steward | 只读采集、生成本地建议、对照人的实际决定评测 | 不公开写入、不启动实现、不修改用户工作区；这是第一里程碑 |
| L2 有界准备 | 在单独授权范围内准备本地提案或隔离实现，提交给人审阅 | Project promotion、PR submit 仍保持各自的明确授权；限制并发、调用与预算 |
| L3 受控推进 | 对指定低风险已审阅任务执行允许的跟进步骤 | 每个动作需新鲜证据和持久审计；高风险与不确定结果升级给人 |
| L4 有界低风险合并 | 在未来经审核的动作权限及独立评审机制下推进低风险 PR | 服务端保护、精确版本、可信验证及审批持续有效；不能自动修改自身规则 |

不能通过设置一个“自动化=true”跨越等级；当前明确授权的 batch/merge 也不能据此被描述成已实现
L3/L4。涉及公开写入的目标等级，需要对应实现 Issue 明确如何表达授权、如何撤销，以及如何与现有
独立 submit/promotion/merge 开关兼容。在这些 Issue 合入之前，现有开关和高风险人工门槛保持原样。

低风险不由改动行数或模型信心决定。CI、身份权限、发布、Runner/网络、数据库、依赖及安全路径
至少沿用现有高风险分类；未知路径、缺失证据、来源不清或保护规则读取失败不能当作低风险。
精确工作流审批只准许对应文件内容通过路径门禁，不能改变其高风险合并分类。

## 治理章程与每步决策

未来章程应存于维护者拥有的可信配置层，版本化并可追溯；本 RFC 不新增可复制即生效的配置模板。
章程至少包含：

- 使命、允许管理的服务/账号/仓库、优先级及明确排除项；
- 允许的动作与自治等级、有效期、预算、并发上限、风险路径和独立审批要求；
- 可信验证命令、模型/客户端能力、知识来源、上下文与数据保留边界；
- 晋升评估窗口、质量门槛、停止条件、接管人、撤销与恢复步骤。

项目中的 AGENTS.md、skills、Issue 正文、评论、网页和模型产物都是被读取的内容，不能授予用户层
权限。贡献规则可以进一步收紧行为，模型不能通过改文档来降低门禁。

建议计划引用当前 WorkItem、operation、仓库/账号/PR 的稳定身份、head/base、规则版本、来源及
观察时刻。执行阶段再次读取必要事实；来源缺失、head/base 变化、权限撤销或方案摘要变化时重新
规划和审核。复用已有任务、队列、verification、publication/merge journal，避免重新实现状态机。

远程写入前持久保存 intent，写入后保存结果。超时或进程中断先核对精确目标，明确区分未发送、
已失败、已成功与结果未知；未知结果不触发普通重试。不能把当前“看起来不存在”当作历史未成功的
证明。GitHub 的 head SHA 条件不等于原子绑定所有基线、规则和评审事实，能力声明应如实说明。

## Issue 治理与 PR 生命周期

Issue 第一阶段以建议和 Project Draft 为主：给出重复候选、待补信息、优先级及建议理由。需要
公开标签、分配或关闭操作时，后续实现应提供原值、目标值、稳定 ID、审阅与恢复条件；不批量自动
评论，也不覆盖维护者或贡献者后续修改。公开通知和历史活动不可真正撤销，必须计入动作成本。

新 Issue 继续通过线上 Project 草稿、最新重复/安全审查、review digest 和独立 promotion。安全报告
进入私下流程。外部认领、贡献审批和仓库约定属于硬门槛，不能用任务排名或优先级覆盖。

PR 从单个已审阅 Issue 出发，使用独立分支/工作区，完成隔离验证与审阅后显式提交。反馈处理复用
当前 PR，保留原作者；#149 的贡献登记完成前，不把外部 PR 伪装成自产 run。每次变更 head/base 或
必要检查，都重新评价证据和审批。合并后再独立规划分支清理，保留 fork、共享及未合并关闭的分支。

## 上下文、记忆与技能改进

短期连续性由任务契约、Checkpoint、未完成事项、验证和最新 head/base 表达；原生聊天或 session
可用于恢复速度，但不是唯一事实来源。压缩须保留来源指针和失效条件，不能丢弃权限、阻塞、风险及
下一步的必要信息。源代码索引可重建；问答应能返回代码/测试位置并表明证据是否陈旧。

长期知识按项目、任务和通用范围显式区分，记录来源、适用版本、支持与反例、审核状态、撤回或过期
原因。跨仓库搬运知识前重新验证适用性；相互矛盾的观察应展示冲突，不能只留下最近或最乐观的摘要。

技能改进目标流程是：**使用采集 → 有来源的候选 → 离线回归 → 有界真实任务对照 → 维护者审批 →
版本化发布 → 可撤回/回退**。每一步属于后续可验收能力，不能把已有采集直接称为自动自进化。
模型可以提议修改技能，不能直接修改可信配置、发布门禁或受保护的 AGENTS.md 来获得能力。

比较至少记录：任务类型、代码与技能版本、实际使用、完成质量、独立验证、接续遗漏、返工、人工
修正时间，以及可获得的 input/cache/output token 和费用。未知用量保持 unknown；统一计入失败与
重试，避免只选择成功样本。合成 benchmark、字符串缩短或格式校验不能证明模型收益。

## 第一里程碑：Shadow Steward

此里程碑需要新的聚焦实现 Issue，目前不会自动安装定时器或启动模型角色。建议的最小闭环是：

1. 维护者选定 RepoSteward 自身与一组已有任务，手动触发只读快照，记录完整性和预算。
2. Steward 在限定上下文中输出少量下一步建议，每项附来源、阻塞、失效条件及预计成本。
3. 维护者实际选择推进、修改或拒绝；保存理由，但不把历史对话当作未来授权。
4. 对比建议与人的决定，回看遗漏、重复建议、事实错误、读取成本和实际节省时间。
5. 汇总真实样本及反例，先修复数据/理解问题，再决定是否申请一个具体动作的 L2 权限。

验收应证明：无公开写入和工作区修改；输入预算有界；缺失/过期事实明确展示；每条建议可追溯；
拒绝理由可记录；重复运行不重复制造任务；失败可停止且不阻塞人工工作。离线 fixture、真实只读
试运行和维护者评估分别记录，不能相互替代。

## 晋升、降级与异常处理

晋升由维护者针对上述作用域显式决定，依据章程规定的评估窗口、样本量、任务质量、人工纠正和
成本。没有可比较样本时维持当前等级，不以固定“成功几次”替代质量判断。单个项目的成功不会自动
授予另一项目权限；供应商/模型大版本、验证配置或任务类型变化后重新建立适用证据。

发现身份或权限不匹配、证据过期、验证失败、预算耗尽、重复副作用或结果未知时，停止受影响任务
的后续写入并保留事实。涉及凭据、隔离或治理规则的异常，应降回只读/人工状态并按私下流程处理。
急停目标是停止领取新任务、阻止新写入、取消可取消的执行并继续只读对账；已送达 GitHub 的动作
不能靠终止本地进程撤回。恢复必须由维护者确认真实远程状态及新授权，不清空失败记录。

模型/规则版本回退、权限撤销和远程变更回滚是不同操作：回退本地版本不自动撤销已发布 PR、合并
或数据库升级。工作台应区分三者，并展示当前控制范围、在途动作和需要人工接管的原因。

## 后续建设顺序

1. 完成精确权限与评测留存（#124、#90），使审批和质量证据可核验。
2. 交付 #149 的已有贡献者 PR 来源登记，补齐真实维护流程中的原生接收入口。
3. 为 Shadow Steward 单独提出实现 Issue，先验证只读建议与真实任务效果。
4. 在试点证明接续遗漏和收益后，再分别评估 #105 hooks、#106 Claude Code、#107 Copilot 托管。
5. 按已有数据决定知识冲突解释、技能候选晋升及工作台细化；每项保持独立验收与回退路径。

本 RFC 不批量关闭这些 Issue，也不将尚未实现的自治能力写成产品现状。长期建设以反复获得真实
维护效果为准，而不是以协议数量、角色数量或自动化程度作为完成指标。
