# 导入项目

本地工作台的“项目 → 导入项目”支持 GitHub HTTPS / SSH 链接和本地绝对目录。识别是显式队列操作，读取当前账号与仓库信息；刷新页面可以回到同一导入记录。输入链接不能包含密码、令牌、查询参数或其他主机。

识别完成后选择：

- **关联已有目录**：登记 Git 工作区，保留未提交文件、当前分支与 origin。计划记录目录身份和内容摘要；执行前发生变化时需要重新生成计划。
- **克隆到新目录**：使用宿主 SSH，在指定父目录下创建暂存目录，完成后以 Linux `renameat2(RENAME_NOREPLACE)` 发布到新目录。平台或文件系统不支持此操作时停止，不退回覆盖式 rename。目标已存在时不会覆盖。
- **仅关注 GitHub**：建立没有工作区的项目，之后可同步 GitHub 或再关联已有目录。

“长期维护 / 参与贡献 / 关注学习”是项目用途。导入不修改可信仓库策略，也不会自动授予执行、提交或合并权限。

## 身份与恢复

同一主机的 GitHub 仓库 ID 用于确认稳定身份；HTTPS、SSH、历史改名及路径通过别名关联。既有 project_id 和 binding_id 保留。仓库名被其他仓库重新占用、不同旧项目占用了同组别名时会停止，需核对后重新计划。Fork 与上游信息来自明确的仓库响应。

识别、计划、执行都有持久记录。确认同一计划多次会复用操作；取消只适用于尚未开始的操作。失败后通过“执行记录与重试”恢复。账号、仓库、目录或登记库发生变化时，应重新识别/计划。

跨台账与登记库写入采用持久步骤与登记库回执。登记成功后即使工作区关联失败，项目仍保留；重试核对已完成步骤，不把部分完成误报成全部回滚。SSH 失败留下的暂存目录不会自动删除；后续重试使用新的子目录。目录发布成功但结果记录中断时，通过已记录的目录身份核对并继续。

克隆使用 SSH agent 或默认 SSH 身份；SSH 必须已经信任对应主机，且能以非交互方式访问仓库。Git 不读取宿主全局配置，不运行模板、hooks、子模块或全局 smudge filters；API 凭据仅进入 REST 客户端。SSH 错误原文不会写入页面或台账。

## 升级既有安装

停止工作台和其他写入者后运行 `reposteward state plan`，核对状态目录与计划摘要，再按 CLI 提示执行 `state upgrade`。计划同时检查任务台账和 `projects.sqlite3`；GET 和服务启动不会迁移旧库。

升级先锁定并备份全部现存数据库，再运行迁移。备份格式 2 包含两个库各自的校验和，`state inspect-backup` 继续支持旧格式 1。SQLite 分库提交不宣称跨库原子性：中断时清楚记录已提交、未提交和结果未知的数据库；核对备份与新计划后，只升级仍待迁移的库。

本阶段不会自动扫描用户其他目录，也不会自动启动 coding agent。导入后的工作区理解与任务接续通过各自显式操作进行。

实现依据：[Linux rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html)、[Git clone](https://git-scm.com/docs/git-clone)、[GitHub repository REST API](https://docs.github.com/en/rest/repos/repos#get-a-repository)。
